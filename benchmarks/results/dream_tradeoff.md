# Dream triage tradeoff evaluation

Generated by `benchmarks/dream_tradeoff.py` from content-free JSON snapshots. Corpus: `dream_tradeoff_corpus.jsonl`. No live model call, no production chat content.

**Verdict (d9fc248 vs cc814ce): `NOT_ACCEPTED`**

The optimization reduces cost, but the frozen corpus shows an unacceptable memory-quality loss under the pre-registered thresholds. It is not acceptable as-is; the recommendations below name the next tuning targets. This issue intentionally does not change the triage algorithm.

Quality: important-fact recall 15/23 (65.2%; target >= 85.0%); self-impression coverage 0.0% (target >= 85.0%). Efficiency: calls -80.0%, tokens -72.8%. Pending growth: 8.0 topics/night, bounded=no.

The baseline `cc814ce` is the comparison anchor, not an acceptable configuration: it extracts every topic, including low-value chatter (false-memory rate 20.5%). The target improves false-memory and duplicate rates, but the memory coverage checks above decide whether that improvement is worth the tradeoff.

### Method

- Every target runs the production `DreamCycle -> IngestService.flush` path against an isolated in-memory SQLite store.
- `d9fc248` and later checkouts are called with `triage=True`; `cc814ce` predates the parameter, so the harness filters unsupported kwargs and runs the same production flush path without triage. The feature-detection table records this difference.
- The model is a deterministic provider that returns frozen extraction items keyed by the Source ids rendered in the production prompt. It never calls the network.
- Sources are admitted through `ExtractionRepository.enqueue_extraction`, the same path `Buffer.add` uses. Artifacts are written only by `IngestService`; the harness never calls `commit`.
- Self-impressions are produced by the production `maintain.self_impression.build_self_impressions` maintenance path.
- Token usage is estimated from the actual prompt/output length with `int(chars/1.6) + 4*messages`; `usage_cached` is zero because no prefix cache is simulated. All targets use the same estimator.
- One target per process avoids importing production modules from two checkouts into the same interpreter.

### Recommendations

1. Extend first-person/possessive triage coverage for the eight missed fact classes: `我对X过敏`, `搬到X`, `我的生日`, grandparent kinship, habit change (`戒烟/戒酒`), `我在X工作`, `我最好的朋友`, and stress/insomnia without a high-arousal keyword. Keep the triage pure and local; this issue does not change it.
2. Decouple bot-behavior episode admission from user-memory triage, or add a behavior-first selection lane. One missed comfort reply reduced self-impression coverage from 1/1 to 0/1 because the impression requires three distinct episodes.
3. Add a bounded pending policy: age-based escalation/re-triage or an explicit discard after N nights. The current Dream-only path keeps both low-value and labeled-important topics pending forever.
4. Keep same-session batching. It produced the measured call and token reduction with zero duplicate regression and no observed output overflow on this corpus.
5. Add a holdout corpus before tuning on these numbers; do not tune thresholds on the same 40 topics used for the report.
6. Re-run this harness after every signal, batch or pending-policy change, and keep the `cc814ce` / `d9fc248` comparison in the results directory.

### Limitations

- The corpus is hand-authored and synthetic (40 topics); it is not a representative sample of real users, languages or group dynamics.
- The fake provider returns pre-recorded extraction items. Parse errors, schema failures, provider variance and true model hallucination are out of scope. 'False memory' here means artifacts produced from labeled low-value chatter, not a measurement of model hallucination.
- Token usage is a character-based estimate, not provider-reported; `usage_cached` is zero because no prefix cache is simulated.
- No live AstrBot host is started; host-layer tests remain skipped in CI shells.
- One deterministic clock and one run per target; no sampling or confidence interval is reported.
- The committed snapshots were produced on `win32` (`environment.platform=win32`). That field is historical provenance, not a cross-platform assertion; the in-memory store, fixed clock and deterministic provider keep the counts platform-independent.
- `d9fc248` and the current tree share the same production extraction code, so their identical metrics validate the harness rather than a new production change.
- `cc814ce` predates the triage and budget parameters. The harness filters unsupported kwargs and runs the same production `DreamCycle -> flush` path without triage; this is the only adaptation.

### 后续建议

1. 补齐八类漏判事实的第一人称/所有格分诊覆盖：`我对X过敏`、`搬到X`、`我的生日`、祖辈亲属、习惯改变（`戒烟/戒酒`）、`我在X工作`、`我最好的朋友`，以及未命中高强度情绪词的压力/失眠。分诊保持纯本地；本 issue 不修改它。
2. 将 bot 行为场景准入与用户记忆分诊解耦，或增加行为优先的选择通道。一条安慰回复被漏掉，就使自我印象覆盖从 1/1 降到 0/1，因为印象需要三个独立场景。
3. 增加有界 pending 策略：按年龄升级/重新分诊，或在 N 晚后显式丢弃。当前 Dream-only 路径会让低价值和标注为重要的主题都永久 pending。
4. 保留同会话批处理。在本语料上，它带来了实测的调用/token 下降，重复率没有回退，也没有观察到输出截断。
5. 在按这些数字调参前增加 holdout 语料；不要用报告所用的同一批 40 个主题来调阈值。
6. 每次修改信号、批处理或 pending 策略后重跑本评估，并在结果目录中保留 `cc814ce` / `d9fc248` 对比。

| `benchmarks/data/dream_tradeoff_corpus.jsonl` | 冻结合成语料 | 变更时必须配套新的快照集和报告 |

仅 `dream_tradeoff_current.json` 预期随当前树变化，用 `python benchmarks/dream_eval.py --repo . --label current --output benchmarks/results/dream_tradeoff_current.json` 重新生成；再基于三份快照用 `python benchmarks/dream_tradeoff.py --input cc814ce=benchmarks/results/dream_tradeoff_cc814ce.json --input d9fc248=benchmarks/results/dream_tradeoff_d9fc248.json --input current=benchmarks/results/dream_tradeoff_current.json --baseline cc814ce --target-label d9fc248 --output-json benchmarks/results/dream_tradeoff.json --output-md benchmarks/results/dream_tradeoff.md` 重建聚合与报告。不要原地重生成 `cc814ce` / `d9fc248`。详细政策见 `benchmarks/results/README.md`。

### 限制

- 语料为手工编写的合成数据（40 个主题），不能代表真实用户、语言或群聊动态。
- fake provider 返回预记录的抽取结果。解析错误、schema 失败、provider 波动和真实模型幻觉不在范围内。这里的“错误记忆”指由标注为低价值闲聊产生的 Artifact，不是对模型幻觉的测量。
- token 用量是基于字符的估算，不是 provider 上报值；由于没有模拟前缀缓存，`usage_cached` 为零。
- 不启动真实 AstrBot host；host 层测试在 CI shell 中仍会跳过。
- 每个目标使用一个确定性时钟和一次运行；不做采样，也不报告置信区间。
- 已提交快照在 `win32` 生成（`environment.platform=win32`）。该字段是历史来源，不是跨平台断言；内存存储、固定时钟和确定性 provider 使计数与平台无关。
- `d9fc248` 与当前工作树共享同一套生产抽取代码，因此指标相同；这说明评估器可复现，而不是新的生产变更。
- `cc814ce` 早于分诊和预算参数。评估器过滤不支持的参数，仍走同一条生产 `DreamCycle -> flush` 路径，只是不启用分诊；这是唯一适配。
